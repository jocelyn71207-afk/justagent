Notion 整合 — 3 種設計方向

API Key 認證 · Properties + Page Body · 每 row = 一筆知識條目

A

擴充現有 ApiSource

在現有 ApiSource interface 加入 sourceType: 'NOTION' 和 Notion 專用欄位，ConnectApiWizard 加入 Notion 分支流程。

新增欄位：
sourceType: 'NOTION' | 'REST'
notionDatabaseId, notionTitleProp, notionCategoryProp, notionTagsProp, includePageBody

優點

  • 複用現有 store 方法
  • 改動範圍小

缺點

  • ApiSource 設計為 REST，Notion 結構差異大，欄位混雜
  • wizrd 邏輯分支複雜
B

獨立 NotionSource（仿 SharePoint 模式）

建立專屬 NotionSource interface 和 NotionConnectWizard，跟 SharePointWizardModal 平行，在 DataSourceTab 並列顯示。

NotionSource interface：
id, name, apiKey, databaseId
titleProp, contentProp, categoryProp, tagsProp
includePageBody, schedule, enabled
lastSyncAt, lastSyncStatus, lastSyncCount, lastSyncError
NotionConnectWizard 步驟：
Step 1：填入 Integration Token + Database ID → 驗證連線
Step 2：預覽 Database Properties → 對應標題/分類/標籤欄位
Step 3：設定知識條目名稱前綴、同步頻率、分類

優點

  • 職責清晰，不污染 ApiSource
  • UX 針對 Notion 優化（可顯示欄位名稱、預覽資料）
  • 仿現有 SharePoint 模式，架構一致

缺點

  • 新元件較多
C

通用整合平台框架

建立 IntegrationSource 抽象層，Notion 是第一個實作，未來 Google Drive、Slack 也用同一套框架接入。

架構：
IntegrationSource（抽象）
├── NotionIntegration
├── GoogleDriveIntegration（未來）
└── SlackIntegration（未來）

每個 integration 實作：connect(), sync(), mapToKnowledge()

優點

  • 擴展性最高
  • 未來加新整合成本低

缺點

  • 過度設計，目前只有 Notion 一個需求
  • 抽象層增加開發成本

我推薦 方案 B：獨立 NotionSource，仿 SharePoint 模式。 架構清晰、UX 可針對 Notion 優化，且與現有程式碼風格一致。 方案 C 在目前只有 Notion 需求時屬過度設計。
