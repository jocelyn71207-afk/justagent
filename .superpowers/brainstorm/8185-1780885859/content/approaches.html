「更新原始檔案」流程 — 3 種設計方向

兩個入口（知識頁 + 資源庫）、手動觸發、自動建立 MINOR 草稿

A

統一 Modal 流程

兩個入口最終都進入同一個「更新來源」Modal，Modal 內統一處理「上傳新檔」或「從資源庫選取」，完成後自動建立 MINOR 草稿。

知識頁入口：
列表「來源已更新」badge → 點擊 → UpdateSourceModal → 上傳/選取 → 建立草稿

資源庫入口：
點「替換新版本」→ 上傳成功 → 彈出 UpdateSourceModal（顯示受影響知識）→ 使用者決定立即建立草稿或稍後處理

優點

  • 邏輯集中，易維護
  • 兩入口體驗一致

缺點

  • Modal 較複雜（需含上傳 + 資源庫選取 + 知識列表）
B

入口分離、輕量連結

資源庫負責「管理檔案版本」，知識頁負責「決定是否重新轉換」，兩者透過 stale 標記連結，各自流程保持輕量。

資源庫入口：
「替換版本」→ 上傳 → 完成（系統背景標記知識 stale）→ 資源庫不再介入

知識頁入口（來源過期）：
banner 提示「來源檔案已有新版本」→ 3 個選項：
① 用新版重新轉換（建立草稿）
② 自行上傳替換來源（走上傳流程）
③ 稍後處理

優點

  • 每個頁面職責清晰
  • 知識頁流程更聚焦

缺點

  • 資源庫側不主動提醒知識影響
  • 使用者需自己知道去知識頁處理
C

雙向通知 + 統一 Wizard

兩個入口都主動顯示影響範圍，並引導進入同一個「更新來源 Wizard」，Wizard 分步驟：選擇來源 → 確認影響 → 觸發轉換。

資源庫入口：
替換版本成功 → 彈出「此檔案關聯 N 筆知識條目，是否立即更新？」
→ 進入 UpdateSourceWizard Step 1（勾選要更新的知識條目）

知識頁入口：
「來源已更新」badge → 點擊 → 進入同一個 Wizard Step 2（選擇使用資源庫版本 or 重新上傳）

Wizard 最後統一顯示「將建立 N 個 MINOR 草稿」確認畫面

優點

  • 批次更新多筆知識時體驗最佳
  • 兩端都有主動引導

缺點

  • 開發成本最高
  • 單筆更新時 Wizard 感覺繁重

我推薦 方案 B：入口分離、職責清晰，且符合目前的架構（resourceStore 管檔案，knowledgeStore 管知識）。對大多數情境夠用，不過若一個檔案同時關聯多筆知識，方案 C 的批次體驗會更好。
